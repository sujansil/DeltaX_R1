# LeaderBoard Puzzles — Round 1

Backend-first FastAPI implementation for Round 1(a) WizTime and Round 1(b) Math Rally.

## Architecture

- FastAPI: API layer
- PostgreSQL: durable state, questions, teams, submissions, score events
- Redis: short-lived coordination/cache/leaderboard acceleration
- Server-authoritative timestamps: browsers never decide scoring/deadlines
- Static HTML/CSS/JS: intentionally simple player/admin UI

## Important configuration

Authentication supports both logistics at the same time. When an admin creates a team
with a password, that password works immediately. When the password is omitted, the API
returns a one-time activation token that the team uses to choose its password.

Exactly one session can be active per team. In Round 1(b), the device is passed to the
four players in order. Logging out releases the session; an admin can also release a
stuck session.

## Run locally

For an interactive menu that manages a persistent, loopback-only preview, run from the
project root:

```bash
./start.sh
```

The script resolves all project paths from its own location, so invoking it by relative or
absolute path also works when your current directory is elsewhere.

The menu starts PostgreSQL, Redis, and Uvicorn; shows status and logs; runs the isolated
test suite; applies explicitly confirmed local-development migrations; and stops preview
services without deleting their database volume. Preview runtime secrets and logs live in
the Git-ignored `.preview/` directory.

The underlying manual workflow is:

1. Copy `.env.example` to `.env` and change SECRET_KEY.
2. Start dependencies:

```bash
docker compose up -d
```

3. Create a virtual environment and install:

```bash
python -m venv .venv
source .venv/bin/activate        # Linux/macOS
# .venv\Scripts\activate         # Windows
pip install -r requirements.txt
```

4. Create tables:

```bash
alembic upgrade head
```

5. Start:

```bash
uvicorn app.main:app --reload
```

API docs: http://127.0.0.1:8000/docs

Player UI: http://127.0.0.1:8000/player/

Admin UI: http://127.0.0.1:8000/admin-ui/

## Test against disposable PostgreSQL

From the project root, run:

```bash
./scripts/test_postgres.sh
```

The command creates an isolated Docker Compose project with a temporary `round1_test`
database on a dynamically assigned localhost port, applies all Alembic migrations, and
runs the complete test suite. Database tests additionally require a test-only guard value
and refuse non-local or differently named databases. The container and its temporary data
are removed when the command exits, including after a test failure.

Plain `pytest` also works from the project root. Without the guarded disposable database,
database-marked tests are skipped.

## First admin

Use the SQL in `scripts/create_admin.sql` after creating the database, replacing the password hash with an Argon2 hash generated by the application's helper.

For a quick development setup, use the `/api/admin/bootstrap` endpoint once, then disable/remove that endpoint before D-day. It is intentionally guarded by `ENVIRONMENT=development`.

## Production notes

- Put FastAPI behind HTTPS.
- Use managed PostgreSQL and Redis.
- Put question images in object storage/CDN rather than local disk.
- Run multiple API workers. Do not store authoritative state in process memory.
- Keep PostgreSQL transactions short.
- Use Redis only as an acceleration/coordination layer; submissions and score events are durable in PostgreSQL.
- Put an external load balancer in front of the workers.
- Before D-day, run the included concurrency tests against staging with at least 250 simulated teams.

## Round 1(a)

Admin starts the round globally, revealing question 1. Each question closes after 30 server-timed seconds. Between questions, players wait until the admin clicks Reveal next question in the live dashboard. The server rejects early advances and late submissions. Question 23 closing completes the player round. The score is calculated from the server's high-resolution timestamp:

0–10s: 1000
10–25s: 1000 - 50 * elapsed_seconds_after_10
25s: exactly 250
25–30s: 250
Wrong: -500
Timeout/unanswered: 0

The client countdown is display-only.

## Round 1(b)

`POST /api/r1b/start` prepares a team's relay after the admin opens R1B but consumes no
time. Player 1's successful `POST /api/r1b/ready` atomically reveals question 1 and starts
the team's persisted 28-minute budget.

One team has four ordered turns and one total 28-minute budget.
A player may submit or skip once. After the turn is permanently closed, the device is
passed to the next player, who must click READY.

At the 28-minute deadline, the backend closes the team. The browser attempts submission
before the displayed deadline, but late answers are never accepted.

Numerical answers use configurable absolute/relative tolerance per question.

Before R1B starts, an authenticated admin reads or changes its mode with
`GET /api/admin/r1b/timer` and `PUT /api/admin/r1b/timer`. The mode is locked once the round
starts. `CONTINUOUS` consumes time during active questions and handovers after Player 1
READY. `PAUSE_DURING_HANDOVER` consumes time only during active questions. Global admin
pause freezes both modes.

The persisted clock invariant is: `remaining_time_ms` is the frozen budget at
`clock_running_since`; while that anchor is non-null, effective remaining time is the
stored budget minus server elapsed time and the deadline is their sum. A null anchor means
the budget is frozen and no deadline applies. Global pause evaluates running clocks at
`paused_at`; resume shifts their anchors and deadlines by exactly the pause duration.

## Transaction ordering

Competition writes lock the round row first, then the team's R1B state row when needed,
then write submissions and score events. Player transitions use a shared round lock, so
different teams can proceed concurrently. Pause, resume, end, and R1A reveal use an
exclusive round lock and briefly serialize against player transitions. Authoritative time
is sampled after lock acquisition so time spent waiting for a lock cannot make a late
submission or READY acceptable.

## Leaderboard publication

Scores can change internally without changing the public board. Admin explicitly publishes a snapshot. The public endpoint returns the last published snapshot until another publication occurs.

## Images

Question/option image fields are URL/path references. The included local storage service saves PNG/JPG uploads under `MEDIA_ROOT`. Replace it with S3/R2/etc. by implementing the same service interface.
